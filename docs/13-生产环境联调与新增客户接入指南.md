# 13. 生产环境联调（Redis/MySQL）与新增客户「纯配置」接入指南

本篇覆盖两件落地事项：
1. **生产 Redis/MySQL 环境联调**：如何把系统从本地 H2 切到生产级 MySQL（平台库）+ Redis（分布式锁），以及 Flyway 数据库迁移的管理方式。
2. **后续新增客户方案扩展配置**：如何在**不改代码**的前提下，用平台基础能力接入一家全新客户（附可运行验证）。

---

## 一、生产环境联调（Redis/MySQL）

### 1.1 profile 与配置分层

| 环境 | profile | 平台库 | schema 管理 | 分布式锁 |
|---|---|---|---|---|
| 本地/测试 | 默认（不激活 prod） | H2 内存库 | JPA `ddl-auto=update` | 内存锁（单机） |
| 生产 | `prod` | MySQL 8 | **Flyway 迁移** + JPA `validate` | **Redis 锁** |

- 默认 `application.yml`：`spring.flyway.enabled=false`，H2 自动建表，便于单测与本地起步。
- 生产 `application-prod.yml`：MySQL 数据源 + Flyway 迁移 + Redis 锁（`perf.lock.redis=true`）+ 开启 Redis 健康检查 + 关闭演示数据播种（`perf.seed.enabled=false`）。

### 1.2 数据库迁移（Flyway）

- 迁移脚本目录：`backend/perf-api/src/main/resources/db/migration/`
- 首个基线：`V1__init.sql`（与 `db/platform/V1__init.sql` 同源，含多租户、规则配置、核算落地、审计、通知、申诉等全部表）。
- 后续变更**只增不改**：新增 `V2__xxx.sql`、`V3__xxx.sql`，Flyway 自动按版本号顺序应用并记录 `flyway_schema_history`。
- 生产 JPA 设为 `ddl-auto=validate`：仅校验实体与表结构一致，**绝不**由 JPA 改表，schema 唯一事实来源为 Flyway。

> 首次接入已有库：`baseline-on-migrate=true` 会为已存在的库打基线后再增量迁移。

### 1.3 关键环境变量（生产覆盖）

| 变量 | 说明 | 示例 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | 激活生产 profile | `prod` |
| `SPRING_DATASOURCE_URL` | 平台库 MySQL 连接 | `jdbc:mysql://mysql:3306/steel_perf?...` |
| `SPRING_DATASOURCE_USERNAME` / `_PASSWORD` | 平台库账号密码 | `perf` / `******` |
| `SPRING_DATA_REDIS_HOST` / `_PORT` | Redis 地址 | `redis` / `6379` |
| `PERF_JWT_SECRET` | JWT 签名密钥（≥32字节） | 生产必须替换 |

> ERP（各租户 SQL Server 2008+）为**外部只读**数据源，按租户在 `t_tenant` 中登记连接信息，由 `ErpDataSourceRegistry` 动态路由，与平台库解耦，无需在此配置。

### 1.4 一键联调（docker-compose）

`docker-compose.yml` 已将 backend 接线到 `mysql` + `redis`，并激活 `prod`：

```bash
docker compose up -d --build
# 启动顺序：mysql / redis 就绪 -> backend(执行 Flyway 迁移) -> frontend
docker compose logs -f backend   # 观察 Flyway "Migrating schema ... to version 1 - init"
```

联调自检清单：
- [ ] `GET /actuator/health` 返回 `UP`，且 `redis` 组件为 `UP`。
- [ ] 后端日志出现 Flyway 迁移成功记录；MySQL 中生成 `flyway_schema_history` 及全部业务表。
- [ ] 多实例场景下并发核算同一实体：Redis 锁串行化，结果幂等一致（同一 `IdempotencyKey` 不重复落库）。
- [ ] 生产未播种演示数据（`perf.seed.enabled=false`）。

### 1.5 K8s 生产要点

- 通过 `Secret` 注入 `SPRING_DATASOURCE_PASSWORD`、`PERF_JWT_SECRET`；`ConfigMap` 注入 URL/host。
- backend 设置 `SPRING_PROFILES_ACTIVE=prod`；readiness 探针指向 `/actuator/health/readiness`。
- Redis 建议独立实例/主从，锁 key 带租户前缀，避免跨租户串扰。

## 二、新增客户方案「纯配置」接入指南

系统的核心承诺：**新客户 = 配置，不 = 写代码**。所有客户共用同一套引擎
（作用域参数 / 达成率映射 / 阶梯 / 成本 / 计息 / 表达式）与核算编排 `CalcEngine`。
四家既有客户（超扑越 / 岳洋通 / 信桥 / 名亿）与新客户走的是同一条链路。

### 2.1 接入五步法

1. **业务事实取数映射**：把客户 ERP 字段映射到平台 DWD 标准字段（销量、金额、毛利、账期、区域、库别等），配置只读取数 DSL（`SafeSqlCompiler` 白名单编译，防注入）。
2. **配置基础能力参数**：
   - 多维单价/系数 → `ScopeRule`（按区域、品类、库别、账期等维度匹配）。
   - 达成率→系数 → `Band` 档位表。
   - 阶梯/门槛/阶跃/封顶 → `TierRow` + `TierEngine.Mode`。
   - 结算方式驱动成本 → `CostEngine`。
   - 预收/预付/合同滚动计息 → 计息表达式 / `ContractInterestService`。
3. **组装方案核算项**：用 `PlanDef` 定义各核算项 `ComponentDef(code, expression, includeInTotal)`，表达式引用上一步的参数与取数字段，`CalcEngine` 自动拓扑排序、逐项下钻、生成幂等键。
4. **试算校验**：在「政策沙盘 / 模拟器」用真实历史数据回测，比对客户手工口径逐项对齐。
5. **发布走审批**：在规则中心提交规则变更单，经多级串签（或签/委托/加签）、定时/灰度生效、灰度转全量，全程审计留痕。

### 2.2 落地验证（可运行）

新增客户「鑫源钢贸·区域直销」已用**纯配置**方式跑通，见
`backend/perf-calc/src/test/java/com/steel/perf/calc/NewClientExtensionTest.java`：

- 达成率 105% → 系数 1.0（`Band` 映射）
- 区域=华东 → 吨位单价 7（`ScopeRule` 多维匹配）
- 销量 900 吨落 [800,1200) 档整段计价 9000（`TierEngine.step` 整体档）
- 方案 `PlanDef` 编排五个核算项，含负向计息扣减
- 合计 `5000 + 6300 + 9000 + 2000 − 2000 = 20300`，由同一 `CalcEngine` 计算断言通过

该用例与四客户验证 `FourClientValidationTest` 并列，证明扩展新客户**无需改动引擎代码**。

### 2.3 扩展性边界与兜底

- 绝大多数客户可通过上述参数化能力覆盖。
- 若遇到平台能力尚未覆盖的算子（极少数），在 `perf-engine` 新增一个**通用算子**（而非客户专用分支），并补单测沉淀为平台能力，再由配置调用——保持「一个引擎、多客户配置」的架构不被稀释。
